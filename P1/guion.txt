BLOQUE 2: El flujo de ejecución de un programa en Java
INTERLOCUTOR 1:
"Para empezar, es importante repasar la secuencia de pasos que sigue Java desde que escribimos el código hasta que vemos el resultado en pantalla. Todo inicia con nuestro archivo fuente con extensión ⁠.java⁠. Cuando ejecutamos el comando ⁠javac⁠ en la terminal, el compilador procesa ese texto y lo traduce a un formato intermedio llamado bytecode, que se guarda en archivos ⁠.class⁠.  
Posteriormente, el intérprete de Java toma ese bytecode, lo lee instrucción por instrucción y lo traduce a comandos que el sistema operativo puede ejecutar para generar la salida o el output final en la pantalla. Este flujo secuencial de fuente, compilación a bytecode, interpretación y output es la base de todo lo que ejecutamos en el lenguaje."  
BLOQUE 3: Caso Práctico: Calculadora CLI, Scanner y Flujo de Control
INTERLOCUTOR 2:
"En la segunda actividad nos enfocamos en el paradigma estructurado al desarrollar una calculadora por línea de comandos. Para capturar los datos del usuario, instanciamos la clase ⁠Scanner⁠ del paquete ⁠java.util⁠, pasándole como argumento ⁠System.in⁠ para conectarla al flujo de entrada estándar de la consola.  
⁠Scanner⁠ funciona analizando un buffer de memoria donde se almacenan las teclas que escribe el usuario. Este buffer fragmenta el texto en bloques llamados tokens, utilizando los espacios en blanco y los saltos de línea como delimitadores por defecto. Para leer números utilizamos métodos como ⁠nextDouble()⁠, pero tuvimos cuidado con la limpieza del buffer: cuando lees un número y luego pides un texto, el salto de línea ⁠\n⁠ se queda atascado en la entrada, por lo que usamos un ⁠nextLine()⁠ adicional para consumir ese salto pendiente y evitar que el programa se salte lecturas.
Toda la aplicación se mantiene activa con un ciclo ⁠do-while⁠ que despliega un menú de 8 opciones y no finaliza hasta seleccionar la opción de salir. Cada elección se evalúa con una estructura ⁠switch⁠, donde para suma, resta y multiplicación capturamos dos operandos, mientras que para la potencia nos apoyamos en el método ⁠Math.pow()⁠ de la biblioteca estándar."  
BLOQUE 4: Programación Defensiva y Control de Excepciones
INTERLOCUTOR 3:
"Ahora bien, el verdadero reto de esta calculadora no fue solo realizar los cálculos, sino garantizar que el software fuera tolerante a fallos. Si un usuario ingresa una operación inválida, la consola no debe abortar de forma abrupta con un error de ejecución. Para evitar esto, aplicamos programación defensiva mediante estructuras condicionales ⁠if⁠.  
Por ejemplo, tanto en la división como en la operación de módulo, el algoritmo evalúa previamente que el divisor no sea igual a cero. Si detecta un cero, detiene la operación y despliega un mensaje claro de advertencia. Del mismo modo, en la raíz cuadrada validamos que el número no sea negativo antes de invocar a ⁠Math.sqrt()⁠. En las pruebas de terminal comprobamos operaciones correctas como dos a la quinta potencia resultando en 32.0, y verificamos que las restricciones detengan los errores de entrada de forma limpia."  
BLOQUE 5: Análisis Arquitectónico de GUI mediante LLM
INTERLOCUTOR 4:
"Para el cierre de la práctica, utilizamos una LLM como herramienta de análisis arquitectónico para una aplicación de dibujo en Java Swing. Mediante Ingeniería de Prompts, le asignamos a la LLM el rol de Arquitecto de Software y le proporcionamos una captura de pantalla de la interfaz para que desglosara los componentes necesarios.
La LLM nos ofreció un análisis modular impecable: identificó el contenedor principal organizado con un layout de tipo ⁠BorderLayout⁠. En la sección superior propuso un panel de herramientas con dos ⁠JComboBox⁠ para seleccionar el color y la figura, un ⁠JCheckBox⁠ para determinar el estado de relleno y componentes ⁠JButton⁠ para las funciones de 'Deshacer' y 'Borrar TODO'. Para la zona central determinó el uso de un ⁠JPanel⁠ con oyentes de eventos de ratón para registrar coordenadas al arrastrar el cursor y almacenar las formas en una lista antes de redibujarlas."
